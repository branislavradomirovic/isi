# ISI SIMPA Methodology v1 - Canonical Design Baseline

Status: **OWNER-APPROVED DIRECTION / NOT YET VALIDATED METHODOLOGY**
Decision date: **2026-09-12**

This document defines the production-methodology design contract for ISI-23. It does not validate any indicator formula, weight, threshold, LISI construction, citizen-level risk model, causal claim, or policy conclusion.

## 1. Purpose

SIMPA is a local social-protection intelligence and monitoring application. Its analytical role is to help authorized institutional users understand the state, capacity, evidence quality, change over time and relationships inside a local social-protection system.

SIMPA is not a citizen-level automated decision engine.

## 2. Safety boundary

SIMPA must not automatically decide or label an individual as:

- eligible or ineligible for a right or benefit;
- high/medium/low social risk;
- suitable or unsuitable for a service;
- fraudulent or suspicious;
- deserving or undeserving of institutional action.

Any later individual-level workflow requires a separate owner-approved architecture, legal/privacy assessment and explicit methodology. This baseline does not authorize one.

Ordinary statistical association must not be described as causation.

## 3. Canonical unit of analysis

Preferred analytical key:

`organization/local system x indicator x reporting period x monitoring cycle x source/version`

Additional dimensions may be introduced only when data governance, privacy and methodology permit them, for example:

- municipality/territorial unit;
- service type;
- institution/provider type;
- demographic aggregate;
- program/intervention aggregate;
- reporting source;
- methodology version.

No identifier for a natural person is part of the default analytical key.

## 4. Evidence and data contract

Every production analytical observation must preserve, where available:

- source identity;
- source version/date;
- ingestion timestamp;
- organization/product scope;
- geographic scope;
- time period;
- unit of measure;
- methodology version;
- quality/validation state;
- missingness state;
- provenance/lineage pointer;
- human validation state where required.

`missing`, `not collected`, `not applicable`, `suppressed`, and numerical zero are distinct states. Missing data must never be silently converted to zero.

## 5. Methodology lifecycle

Minimum lifecycle:

`DRAFT -> PROPOSED -> VALIDATED -> RETIRED`

Rules:

- DRAFT may be authored and tested but is not institutionally validated.
- PROPOSED may be exposed for controlled user testing with explicit labelling.
- VALIDATED requires owner/human methodology approval and supporting evidence/reference calculations.
- RETIRED remains reproducible for historical results but is not used for new production calculations.

Every computed result records the exact methodology version used.

## 6. Analytical layers

### 6.1 Descriptive layer

This is the mandatory first layer for validated data.

Typical outputs may include, only where methodology defines them:

- counts;
- rates and proportions;
- service coverage;
- capacity/utilization;
- geographic distribution;
- period-over-period change;
- trend direction;
- missing-evidence counts;
- provenance coverage;
- data-quality/readiness metrics.

A data/evidence readiness metric must never be presented as a social-risk score or service-outcome score.

### 6.2 Indicator layer

Each production indicator definition must specify:

- stable indicator ID and name;
- purpose and interpretation;
- numerator/denominator or computation rule if applicable;
- unit and scale;
- required source fields;
- eligible population/aggregate scope where applicable;
- time aggregation;
- geographic aggregation;
- missing-data rule;
- suppression/privacy rule;
- quality preconditions;
- reference calculation dataset;
- accepted tolerance;
- methodology lifecycle state;
- owner/approver;
- version and effective dates.

No formula is inferred from a label or generated by an LLM.

### 6.3 Regression and association layer

Model family is selected by target semantics, not by convenience.

Preferred baselines:

- continuous target: Linear Regression;
- regularized continuous target: Ridge or Elastic Net;
- count target: Poisson, with Negative Binomial when over-dispersion warrants it;
- binary/system-state outcome: Logistic Regression;
- proportion/rate target: statistically appropriate binomial/fractional model;
- repeated municipality/system observations: fixed-effects, mixed-effects or hierarchical model where justified;
- simple temporal trend: linear trend, ETS or SARIMAX before more complex challengers.

Challengers may include gradient-boosted tree models when data volume, predictive objective and validation justify them.

Minimum output contract where applicable:

- target definition;
- feature list and versions;
- sample size;
- training/evaluation period;
- coefficient/effect estimate or model output;
- confidence interval/uncertainty;
- fit/error metrics;
- diagnostics;
- missing-data handling;
- model version;
- methodology version;
- limitations;
- explicit non-causal wording unless a separately approved causal design exists.

### 6.4 System-level classification layer

Classification is allowed only for explicitly defined aggregate/system states, for example:

- evidence readiness;
- data completeness;
- service-capacity trend;
- monitoring readiness;
- data-quality state.

Class definitions and thresholds must be methodology-owned and versioned.

Preferred baseline:

- Logistic Regression for binary/multiclass probabilistic classification where appropriate.

Possible challengers:

- Random Forest;
- Gradient Boosting;
- other interpretable or explainable registered models.

Minimum output:

- predicted class;
- class probability;
- calibration information where relevant;
- support/sample distribution;
- explanation;
- uncertainty/limitations.

The UI must not show a bare label such as `HIGH RISK` without probability, context and methodology.

### 6.5 Unsupervised analytical profiling

Possible families:

- K-Means;
- hierarchical clustering;
- Gaussian Mixture or another approved mixture model.

Use only when:

- variables and scaling are methodology-defined;
- cluster stability is evaluated;
- interpretation is human-reviewed;
- labels remain neutral analytical profiles rather than normative rankings.

Preferred wording: `analytical profile A/B/C`, not `good/bad municipality`.

### 6.6 Time/trend analysis

For longitudinal aggregate data:

- preserve temporal order;
- report data gaps;
- avoid random leakage across time;
- use appropriate lag/seasonality controls where required;
- state whether the result is descriptive trend, association model or forecast.

SIMPA forecasting is not assumed by this baseline. Any production forecast requires an explicit methodology and validation protocol.

## 7. Feature governance

Every analytical feature used by a registered model must have:

- stable feature key;
- source lineage;
- data type/unit;
- transformation definition;
- aggregation window;
- missing-value rule;
- sensitivity/privacy class;
- product/tenant scope;
- version;
- methodology/model dependencies.

Sensitive raw data must not be copied into shared cross-tenant or cross-product feature stores automatically.

## 8. Model evaluation

A candidate model must be compared to an explicit baseline.

Evaluation design depends on the problem:

- random or stratified split only where temporal/group leakage is not possible;
- grouped validation where observations are clustered by municipality/system/provider;
- temporal validation where time predicts future time;
- repeated cross-validation where statistically appropriate.

Metrics may include, by problem type:

- MAE/RMSE/R2 for continuous targets;
- deviance and count-specific diagnostics for count models;
- ROC-AUC/PR-AUC only when appropriate;
- precision/recall/F1 where class balance and decision semantics justify them;
- Brier score/calibration curves for probabilistic classifications;
- confidence interval coverage;
- stability across geography/time/subgroups where allowed by privacy policy.

No single metric is sufficient for promotion.

## 9. Explainability and uncertainty

Classical regression display should expose, when statistically appropriate:

- coefficients;
- confidence intervals;
- standard errors or equivalent uncertainty;
- sample size;
- model diagnostics.

Tree/boosting models may expose:

- global feature importance;
- SHAP or equivalent local/global contribution analysis;
- partial dependence where appropriate.

UI wording must state:

`Feature contribution or statistical association does not by itself establish causal effect.`

## 10. Document AI and evidence extraction

SIMPA may use a VLM/document model to assist with:

- OCR;
- table extraction;
- chart interpretation;
- document metadata extraction;
- source classification;
- evidence tagging.

Extracted facts must be marked `EXTRACTED_UNVERIFIED` until deterministic validation or human review confirms them where required.

The extraction model does not validate methodology.

## 11. RAG and knowledge contract

Allowed namespace families remain:

- `PUBLIC/ISI`;
- `PUBLIC/SIMPA`;
- `ORG-<organization UUID>/SIMPA`.

ORDO private context is not valid SIMPA private retrieval context.

Sensitive SIMPA requests preserve the existing local-only AI policy unless a later owner-approved policy change says otherwise.

A dedicated embedding model is used for retrieval. Chat-model hidden states are not treated as an implicit production embedding service.

## 12. LLM synthesis contract

The LLM receives a bounded, structured analytical snapshot rather than unbounded raw institutional data.

Minimum conceptual input:

```json
{
  "period": "...",
  "methodology_versions": [],
  "validated_indicators": [],
  "descriptive_results": [],
  "regression_results": [],
  "classification_results": [],
  "trend_results": [],
  "data_quality": {},
  "missing_evidence": [],
  "retrieved_evidence": [],
  "limitations": []
}
```

Minimum narrative sections:

- Executive Summary;
- Evidence Quality;
- Observed Trends;
- Statistical Associations;
- Attention Points;
- Missing Evidence;
- Limitations;
- Sources/Provenance;
- Human Review State.

The LLM must not fabricate a missing coefficient, probability, score, threshold, forecast or source.

## 13. User-interface presentation contract

Canonical order:

`Evidence -> Indicators/Analytics -> Models -> AI interpretation -> Human review`

Recommended SIMPA surfaces:

### Evidence quality

Show:

- provenance completeness;
- validation completeness;
- missing evidence;
- recency/freshness;
- methodology readiness.

### Indicator views

Show:

- value and unit;
- period;
- methodology version;
- source/provenance;
- trend where valid;
- quality/confidence state.

### Regression/association views

Prefer coefficient/interval plots and a compact table containing:

- term/feature;
- estimate;
- confidence interval;
- model/version;
- sample size;
- diagnostic note.

### Classification views

Show probability/calibration context rather than only a categorical label.

### AI interpretation

Display after the numerical evidence and expose the exact source/model/methodology context used.

### Human review

Provide an explicit review state such as:

- pending;
- accepted;
- rejected;
- accepted with comment.

## 14. Champion/challenger lifecycle

Each SIMPA statistical/ML/embedding/LLM/VLM capability has:

- champion model;
- zero or more challengers;
- eval dataset version;
- metrics;
- approval record;
- rollback target.

No challenger becomes champion merely because it is newer or larger.

## 15. ISI-23 implementation acceptance

ISI-23 cannot close until at minimum:

- production indicator registry contracts are defined;
- every implemented formula has an approved methodology state and reference calculation test;
- no citizen-level automated institutional decisioning is introduced;
- model families are selected per target semantics;
- uncertainty/diagnostics are represented;
- provenance is visible;
- AI synthesis consumes bounded analytical snapshots;
- Help and User Guide explain method, limitations and human-review responsibility;
- DRAFT/PROPOSED outputs cannot be confused with VALIDATED methodology.

## 16. Open methodology items intentionally not decided here

This baseline does not decide:

- LISI formula;
- LISI weights;
- indicator thresholds;
- class/risk bands;
- normative rankings;
- causal estimands;
- production forecast targets;
- institutional policy recommendations.

Those require separate evidence and explicit owner/human methodology approval.
